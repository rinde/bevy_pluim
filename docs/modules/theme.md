# `theme.rs`

`Theme`: the light and dark `ThemeColors`, fonts, rem type scale, radii and shadows, with the WCAG contrast guard.

Read this before changing `src/theme.rs`. When the module's behavior changes, update this file in the same PR.

## Details

`Theme` resource (colors, `body_font` and `display_font` handles defaulting to Bevy's font with the application loading its own, the `font_size_*` type scale, in logical pixels at Bevy's default rem size of 20 px, which every widget turns into `FontSize::Rem` with `Theme::font_size(px)` (its own constant sizes too), so the text follows Bevy's `RemSize`: an app that raises `RemSize` scales the widgets' text, at the default nothing moves; sizes tied to text stay `px` unless a `[text 1.5x]` scenario shows them clipping (only the badge is in rem), `control_radius` for buttons, list items, steppers and scroll bars and `panel_radius` for `Card` and `Float`), `ThemeColors` (also the text, divider, accent, danger, warning, info, pill, segmented, card and chip slots of the redesign, and `slider_track` / `slider_fill` for a `Slider`; both defaults use a dark `large_shadow` and `small_shadow`, black, so neither theme glows; both meet WCAG AA contrast (4.5:1 for their text and ink pairs, 3:1 for `focus_ring` and `selection_ring`), guarded by `the_default_themes_meet_wcag_aa_contrast`, which lists every pair a widget draws (an `ItemNote`'s ink on the item backgrounds is `list.rs`'s `note_ink`, which falls back to `text_primary`; `theme.rs`'s crate-private `contrast_ratio` is shared by both), which exempts `text_disabled`, `text_tertiary` and the decorative borders; the shadow constants set color only, offsets stay with the widgets; `Pill` and `Badge` share `pill_background` / `pill_text`), `DEFAULT_LIGHT_THEME_COLORS` / `DEFAULT_DARK_THEME_COLORS`, `ThemeMode`, `Theme::with_colors(light, dark)` for an app's own pair, `set_mode` / `mode` / `light_dark_toggle` (switch the set in use) and `set_colors` (replace one half of the pair); the set in use is read with `Theme::colors()`, a getter, as the field is private so it cannot fall out of step with the mode (a compile-fail doc example guards that; reflection still reaches `Theme.colors`, as an inspection facility, not an invariant boundary, so scenario files keep their `Theme.colors` paths); `Theme::font_size(px)` returns `FALLBACK_FONT_SIZE_PX` (the body's 15 px, in rem) for a NaN, infinite, zero or negative size, since the public `font_size_*` fields can hold one and it is the boundary to text layout, `colors_of(mode)` / `set_colors(mode, colors)` (read or replace one half of the pair; the latter also updates `colors` when that half is in use, which is how the `ThemeEditor` edits a slot live), the shadow constants; also keeps `ClearColor` in step with the theme

## Restyling text (#762, #778)

A write marks the font changed and makes Bevy lay the whole tree out again, so the `theme_*` systems of `Tooltip` (`restyle_popups`), `Slider`, `NumericStepper`, `TextField`, `Kbd`, `PushButton` (label and icon), `Link`, `Toast`, `Label`, `Pill`, `SettingRow`, `List` (`theme_item_labels`) and `FilterCombo` (its empty line) use `set_if_neq` on a whole `TextFont`, or compare field by field before assigning where they only own some fields (`font`, `font_size`), so a color-only theme change or an unchanged font writes none and a changed font field still reaches the text (`restyling_text_widgets_with_an_unchanged_font_writes_no_text_font`, `restyling_text_widgets_with_a_color_only_change_writes_no_text_font`, `restyling_text_widgets_with_a_changed_font_still_writes_it`; the tooltip popup is not in that test, it needs a showing popup). `TextColor` writes are not covered. A new widget with text follows the same rule.

Tests: `restyling_text_widgets_*`, `restyling_a_toolbar_*` and `restyling_a_showing_tooltip_popup_*` in `tests/headless.rs`.
