# `light_dark_toggle.rs`

`LightDarkToggle`: a Light / System / Dark switch driving the `ThemePreference` resource.

Read this before changing `src/light_dark_toggle.rs`. When the module's behaviour changes, update this file in the same PR.

Cross-cutting design: [keyboard focus and navigation](../design/keyboard-focus.md).

## Details

`LightDarkToggle`: a three-way Light / System / Dark switch, a track of three `LightDarkOption`s (`Button`s; the toggle is one tab stop at the option of the current preference, with arrow keys, Home and End that move the focus and pick the option they land on, a `RovingGroup::marked_radio()`; each a drawn 16 px icon, sun, computer and moon, built by the module as images with the label beside it, no app assets), styled from the `segmented_*` slots like a `SegmentedControl`. The preference's look is an `OptionIndicator` (a crate-private child of the toggle from `indicator.rs`, as for a `SegmentedControl`) that slides to the option of the preference when it changes, also from elsewhere; the options' own backgrounds are transparent, and an option's `TextFont` is written only when it differs (#710, as for the segments and tabs). Spawning it is all an app does: it inserts the `ThemePreference` resource (`Light`, `System` default, `Dark`) when the app has none, and an option's `Activate` sets it. `System` follows the operating system: `SystemTheme` (`Option<ThemeMode>`, `None` until known) is read from the primary window once (not when the window was spawned with a fixed `window_theme`: the crate-private `PresetWindowTheme`, put on by an observer of `Add<Window>` and, in `LightDarkTogglePlugin::build`, on the windows that already exist (`WindowPlugin` spawns the primary one before), keeps it `None`, since winit reports the forced theme back as the window's; `apply_window_theme` marks a primary window it writes a fixed theme to before it was read the same way, so a replacement primary spawned mid-frame never has our theme taken for the system's and its system theme is known from its first `WindowThemeChanged`: `a_replacement_primary_window_with_a_preset_theme_is_not_taken_for_the_system_theme`, `a_replacement_primary_window_given_the_fixed_theme_before_it_is_read_is_not_taken_for_the_system_theme`) and then from Bevy's `WindowThemeChanged` messages of the primary window only (`track_system_theme`, `PreUpdate`, also while a theme is fixed, as far as the platform reports it): a message whose `window` is not the current primary window is ignored, as are all of them while there is no primary window, and a primary window that is a new entity is read once like the first, the known theme staying until then (`theme_messages_of_a_secondary_window_do_not_change_the_system_theme`, `a_fixed_preference_ignores_theme_messages_of_every_window`, `theme_messages_are_ignored_without_a_primary_window_and_a_replacement_is_followed`). The preference sets `Theme::set_mode` (`apply_preference`; `System` before the system theme is known is light) and the primary window's `window_theme` (`apply_window_theme`: `Some` for a fixed preference, `None`, the system's, for `System`). An app fixes light or dark programmatically by inserting `ThemePreference::Light` / `Dark` (before or after the toggle), and one without a toggle never gets the preference, so nothing changes for it. The systems run only while the `ThemePreference` resource exists. To a screen reader the toggle is a `Role::RadioGroup` labelled "Theme" and each option a `Role::RadioButton` labelled with its text, `toggled` while it is the preference (`light_dark_toggle_click_sets_preference.ron`, `light_dark_toggle_keyboard_selects.ron`)

Touch: a tap picks as a click does, a finger that slides off before lifting picks nothing, and no hover look stays after the lift (a finger never hovers); the focus, and so the roving stop, follows the tapped item (`light_dark_toggle_touch.ron`).
