# `segmented_control.rs`

`SegmentedControl`: a track of segments that picks one item, with optional icons.

Read this before changing `src/segmented_control.rs`. When the module's behaviour changes, update this file in the same PR.

Cross-cutting design: [keyboard focus and navigation](../design/keyboard-focus.md), [lists and selection](../design/lists-and-selection.md).

## Details

`SegmentedControl`: a track of `Segment`s (`Button`s; the control is one tab stop, at the selected segment, with the arrow keys moving and picking, a `RovingGroup`) over a `Selection` of `Item<String>`, own or `Selection::Ref`, normally a `One`; a segment's `Activate` sets the selection to its item (`set_selection`), `Selected` and the text colours follow the selection and hover. The selected look is a `SegmentIndicator` (a `segmented_selected` child of the control, absolutely placed behind the segments with `ZIndex(-1)`, spawned by the first frame after the control), which `indicator.rs`'s `animate` slides to the selected segment's laid-out box (exponential ease, `INDICATOR_RATE`, snapping at the first placement and under 0.5 px); the segments' own backgrounds are transparent (`a_segmented_control_slides_its_indicator_to_a_newly_selected_segment`); a segment's `TextFont` is written only when it differs (#710; `restyling_segments_tabs_and_toggle_options_with_an_unchanged_font_writes_no_text_font`). A segment shows the item's text, an icon, or both: an `ItemIcon(Handle<Image>)` next to the `Item<String>` on the item entity (like `ItemNote`; `(Item::new("Auto"), ItemIcon(handle))` works in a `bsn!` too) gives its segment a `SegmentIcon` (a plain 16 px `ImageNode` before the text, 6 px gap, `Pickable::IGNORE`, no accessibility node; not an `Icon`, since no `IconColor` role is `segmented_selected_text`) that `theme_segmented_controls` tints with the segment's text colour (`segment_colors(..).1`), so selection, hover and theme change keep it right (`theme_segmented_controls` given one control, as `selection_change` does, reaches that control's segments, indicator, labels and icons through `Children`, never by scanning all of them: `replacing_one_controls_selection_restyles_only_that_control`, #726). `SegmentLabels::{Shown (default), Hidden}` (immutable, required by `SegmentedControl`, like `ToolbarLabels`) hides the text (`Display::None`) of items that have an icon, which then show the icon alone with a `Tooltip` of the text (one the widget adds and marks with the crate-private `OwnedTooltip` of `tooltip.rs` (shared with `Toolbar`) holding the text it gave it, and removes again when the labels are shown; a `Tooltip` with other text, one the app put on a segment or swapped in over the widget's, is the app's and is never overwritten or removed, the marker being dropped when the widget next looks, so a hidden-label segment of the app's keeps its text; the one limit is a `Tooltip` with exactly the same text as the widget's own, which is indistinguishable from it, so it keeps the `OwnedTooltip` marker and is removed when the labels switch to `Shown`); an item without an icon keeps its text. `sync_icons` updates icon, text display and tooltip in place when an `ItemIcon` is added, changed or removed or `SegmentLabels` is inserted again (`changing_or_removing_an_item_icon_updates_its_segment_in_place`); the accessible name is always the item's text, so an icon-only segment is a named radio button (`segmented_control_icons_*.ron`). `sync_icons` finds a segment's icon and text among that segment's own `Children`, so a change costs work per segment, not per segment times every icon and label in the world (`many_icon_segmented_controls_keep_one_icon_and_hidden_label_per_segment`: 30 controls of 40 segments, 20 frames each changing one icon, 4.6 s before, 72 ms after). `selection_change` looks only at the controls whose own `Selection` or the one they refer to (one `Selection::Ref` hop) changed, so a change to one selection restyles no unrelated control (`a_segmented_control_follows_only_the_selection_it_draws_from`; `segmented-controls-selection-changing` bench workload, #709). Changing the text of an `Item<String>` updates its segment's text in place (`sync_label_text`, also the tooltip of an icon-only segment), and inserting or reordering items puts the segments in the items' order without respawning the others (`order_segments`, linear through `select.rs`'s `items_in_order`; `on_items_changed` reconciles with a set of wanted and a set of shown items, a second segment of one item is despawned, #679; the indicator stays after them) (`changing_an_items_text_updates_its_segment_in_place`, `an_item_inserted_in_the_middle_puts_its_segment_there`, `reordering_items_reorders_their_segments`). `clear_dangling_controls` (after a removed `Selection` or `ItemsRef`, through `unwatch_dangling_items`) clears the segments of a control whose source (the selection behind its `Selection::Ref`) was despawned and recovers when it is pointed at a live source again (`a_segmented_control_is_cleared_when_the_source_behind_its_selection_is_despawned`). It is its own widget, not a `List` style, so `List` is untouched. To a screen reader the control is a `Role::RadioGroup` and each segment a `Role::RadioButton`, `toggled` following `Selected` (`segmented_control_accessible_radio_group.ron`); the segments keep `Button`, so `Role(role: Button, ..)` still finds them
