# `text_field.rs`

`TextField`: a single-line text input with change and commit events.

Read this before changing `src/text_field.rs`. When the module's behavior changes, update this file in the same PR.

Cross-cutting design: [keyboard focus and navigation](../design/keyboard-focus.md).

## Details

`TextField::new(value)` with `with_placeholder`, `with_name`, `with_min_width` / `with_max_width` (`Val`s, `Val::Px(160.0)` / `Val::Px(320.0)` by default: Bevy layout constraints passed unchanged to the field's `Node`, so `Auto`, percentages of the parent, viewport units and the rest work and are resolved by layout, logical pixels only for `Val::Px`; nothing is converted to pixels or compared before layout, and when both resolve with the minimum above the maximum the minimum wins as in Bevy's layout, so a 400 px minimum with the default 320 px maximum is 400 px wide: a documented rule, not an error, neither bound is clamped nor logged; `a_text_field_with_a_minimum_above_its_maximum_is_as_wide_as_the_minimum` and the neighboring layout tests in `tests/scenarios.rs`; inserting a new `TextField` replaces the widths in place, without respawning the input or a `TextFieldChange`): a single-line text input over Bevy's `TextInput` / `EditableText`. The field is a bordered box (1 px `border`, `card_surface`, control radius, 10 / 7 px padding) holding a `TextInput` child (`TextFieldRefs::input`, a tab stop, body text in `text_primary`, no wrap, so the text scrolls inside the box instead of growing it) and an absolutely placed placeholder (`TextFieldRefs::placeholder`, `text_tertiary`, shown while the text is empty). Bevy's `PointerFocusPlugin` gives the input the focus on a click and takes it on a press elsewhere, and an observer of `AcquireFocus` on the box gives it to the input for a click on the box's border too (`text_field_border_click_focuses.ron`); `Enter` (also `NumpadEnter`) gives it up, `Escape` puts back the text from when it took the focus and gives it up (both by key code, so the tester's `Tap` works; Bevy's own `Escape` reads the logical key); both call `propagate(false)`, so neither key bubbles to the field's ancestors (`enter_and_numpad_enter_commit_the_text_and_stop_there`, `escape_puts_the_text_back_without_a_commit_and_stops_like_enter`, `tab_commits_the_text_even_when_it_did_not_change`, `inserting_a_new_text_field_sets_the_text_without_a_change_event` in `tests/headless.rs`, which adds `TextPlugin` so edits apply). Entity events on the field: `TextFieldChange { value }` on every edit (and an `Escape` restore), `TextFieldCommit { value }` when the focus leaves other than by `Escape` (Enter, Tab, a press elsewhere), changed or not. The focus ring is on the box, after a click too (`RingOn` / `RingTarget` in `focus.rs`). Insert a new `TextField` to set the text (no change event), placeholder, name or widths. To a screen reader the input is a `Role::TextInput` with its text as value and `name` as label (`text_field_accessible_text_input.ron`). It needs `TextInputPlugin` and `PointerFocusPlugin` from `UiWidgetsPlugins` (in `DefaultPlugins` and the tester's `HeadlessPlugins`); `WidgetsPlugin` does not add them

**Touch (#803):** a tap behaves as a click: Bevy's `PointerFocusPlugin` focuses the input on a touch press (the box's `AcquireFocus` covers the border), a tap elsewhere takes the focus off and commits (`TextFieldCommit`), and `RingOn` / `RingTarget` follow. No on-screen keyboard is shown: Bevy has no API for it on these targets. Scenarios: `text_field_touch_border_tap_focuses.ron`, `text_field_touch_tap_elsewhere_commits.ron`.

The focus ring after a tap is checked by `Outline` in `text_field_touch_border_tap_focuses.ron`. Caret placement by a tap is not tested: placing the caret from a pointer position needs Bevy's text layout (glyph positions), which the headless harness does not produce, so whether a tap puts the caret where a click would rests on Bevy's `EditableText` handling the pointer press for any pointer, not on code of this crate.
