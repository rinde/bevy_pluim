# `list.rs`

`List`: a `ListBox` of item views over a `Selection`, with layouts, corner styles, notes and custom views.

Read this before changing `src/list.rs`. When the module's behavior changes, update this file in the same PR.

Cross-cutting design: [lists and selection](../design/lists-and-selection.md), [keyboard focus and navigation](../design/keyboard-focus.md), [scrolling](../design/scrolling.md).

## Details

Selection changes are collected and lists visited once per frame (#671; `simultaneous_selection_changes_update_only_the_lists_that_follow_them`).  `List` (and, through the shared `watch_items`, `ColorPalette`) starts watching when its `Selection` or the `List` itself is inserted, whichever comes last, because a scene (`List @{Selection::builder()..scene_with_items(..)}`) inserts them in an order of its own and the `List` can arrive after the selection and items (`the_overview_scroll_area_page_has_rows_and_visible_scroll_bars`); it follows the `ItemsChanged` of the items entity its `Selection` draws from with one observer, remembered in the crate-private `ItemsWatch` on the list: pointing the list at other items (a `Combo` does) despawns the old observer, so the old items no longer touch its views, and the record goes with the list (`a_list_pointed_at_other_items_ignores_changes_to_the_old_ones`); `List` with `ListLayout` (`VerticalGrid { columns: 0 }` is laid out as one column and logs an `error!` when the layout is inserted; `List` requires a `Node` that is a grid, except that `ListLayout::Vertical` (one column, the default) is a flex column (`Display::Flex`, `FlexDirection::Column`), because Taffy lays out thousands of rows in a grid several times slower than in a flex column (`list-items-adding` at 4 000 rows: about 530 ms a frame as a grid, 90 ms as a flex column, #729), and `ListLayout::Horizontal` is a flex row (`FlexDirection::Row`; `list-items-horizontal-adding` at 4 000 rows: 693 ms as a grid, 86 ms as a flex row, #766); only `VerticalGrid` stays a grid. A default row is two entities, the view and its label: hover and press colors come from one global `handle_mouse_events` observer that acts on views with the crate-private `DefaultRow` marker, not an observer entity per row (`a_default_list_row_is_a_view_and_a_label_with_no_observer_entity_and_still_follows_the_pointer`; a palette swatch keeps its own observer and a custom view `handle_custom_view_mouse_events`). Even so a `List` spawns a view per item, and a long list belongs in a `VirtualList`; its hook and an `on_insert` hook of `ListLayout` set only the fields the list owns on the existing `Node` (`display`, `flex_direction`, `position_type`, `grid_auto_flow`, `grid_template_columns`): a `width`, `margin` or `flex_grow` of the app survives, also when `List` is inserted again, and changing `ListLayout` on a live list updates the layout (display, flex direction, grid flow and columns); a `NonZeroU16` would be a public API change) and `CornerStyle` (`Separated` is the panel style: 6 px padding, 2 px gaps, rows rounded on all corners, the selected row with a 1 px `selection_ring` border), a list that does not scroll (`Vertical` and `Horizontal` are flex column and row layouts, only `VerticalGrid` is a grid; rows have `flex_shrink: 0`, so in a narrow `Horizontal` list they keep their content width and overflow, `a_horizontal_list_in_a_narrow_parent_keeps_the_content_width_of_its_rows`), and has no maximum height: wrap it in a `ScrollArea` whose node has a `max_height` and the area grows with the rows up to it and then scrolls (`a_list_in_a_scroll_area_with_a_maximum_height_grows_with_its_rows_and_then_scrolls`; #505 decided against a `List` field for this): a `ListBox` that renders the items of its `Selection` as `ItemView`s (`ListItem`s) and keeps them in sync, `Selected` included; while focused it keeps its arrow, Home and End keys from bubbling on (`keep_navigation_keys`), and lets those of a focused descendant (a button in a row) past (`pass_first_presses_from_descendants`, see [directional navigation](../design/keyboard-focus.md#directional-navigation-is-the-apps)) `on_items_changed` reconciles views and items in linear time (one `HashSet` of the wanted items, one of those that already have a view: a view stays when its item is wanted and no earlier view shows it, any other is despawned; `list-items-initial` and `list-items-adding` bench workloads, #676; `a_list_keeps_its_views_and_their_children_when_items_are_added_and_removed`, `a_list_despawns_a_second_view_of_the_same_item`, `a_list_of_thousands_of_items_gets_one_view_each_and_marks_the_selected_one`) `ItemNote { text, tone }` (`NoteTone::{Secondary, Warning}`; `ItemNote::new` / `::warning`) on an `Item<String>` entity adds a note after the label of its default row, in the caption size and `text_secondary` / `warning_text`, or `text_primary` on a row whose background that tone does not reach 4.5:1 on (`note_ink`, kept in step by `note_ink_follows_row` when the row's background changes: hovered, selected, theme): a `Combo`'s popup shows it, its button shows the label only. Renaming an `Item<String>` in place updates the `ItemLabel` text of its default rows (`sync_item_label_text`, through `NoteViews`, so only the rows of that item, also in lists sharing it; custom views are left alone; `renaming_an_item_updates_the_visible_and_accessible_text_of_every_list_that_shows_it`). The row's accessible name is the label followed by the note (`Delft < unreachable >`, kept by `sync_item_labels`); changing, inserting or removing a note, or giving it empty text, updates the row in place (`combo_option_notes.ron`). `sync_item_notes` looks only at the rows a note change concerns: every default `ItemView` gets the crate-private `NoteViewOf(item)` relationship (put on by `ItemView`'s `on_insert`, target `NoteViews` on the item), so a changed or removed `ItemNote` finds exactly the views of its item, also in several lists sharing it, and a new view is looked at once; a `Theme` change looks at all of them (`a_note_change_resyncs_only_the_rows_of_its_item_and_a_theme_change_all_of_them`; the `list-notes-changing` and `list-notes-idle` bench workloads). A custom view (`ItemViewCreator`) does not get it. `ItemHeader(true)` (a component on the item entity next to its `Item<String>`, set when the item is created; the bool lets one array of items hold headers and options, `build_with_items([(Item::new("A"), ItemHeader(true)), (Item::new("b"), ItemHeader(false))])`, `an_item_header_can_be_attached_through_build_with_items`) makes the item a heading row, for a `Combo` popup too: its view is an `ItemView` without `ListItem` and `Selectable` (and the crate-private `HeaderRow`), so the `ListBox` skips it in arrow, Home and End navigation and a click or Enter never picks it; `on_value_change` is never told of it and `selection_change` leaves it alone. The label is the `ItemLabel` in `text_secondary` and the caption size (`HeaderLabel`, both light and dark themes), the row never takes a hover or selected background, and a screen reader reads it as `Role::Heading` (`sync_item_labels`). A list with an `ItemViewCreator` shows a header the same way and does not run the creator for it. Adding, removing or flipping `ItemHeader` on an item that already has a row does not change that row, and nothing stops an app from putting a header into the `Selection` in code (the widgets only never pick it; an initial selection of a header is not guarded) (`a_header_item_is_a_heading_row_that_keys_and_clicks_skip_and_that_follows_the_theme`). `FilterCombo` hides headers while a query is typed (see [filter_combo](filter_combo.md)).
